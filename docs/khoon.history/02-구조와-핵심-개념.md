# 02. 구조와 핵심 개념

## 패키지

```
com.moneyweather
├─ api            컨트롤러(URL ↔ 서비스), 예외 → JSON 변환, Swagger 설정
├─ service        업무 로직. 여기가 본체
├─ agent          AI: 도구 모음, 답변기(규칙 기반 / OpenAI 호환), 답변기 선택
├─ security       JWT 발급·검증, 인증 필터, 로그인 제한, Spring Security 설정
├─ repository     Spring Data JPA 저장소, 거래 검색 조건(TransactionSpecs)
├─ domain         엔티티, enum, 기본 카테고리
└─ observability  API 요청 로그
```

## 요청이 흐르는 길

```
요청
 │
 ├─ ApiRequestLoggingFilter   가장 바깥. 끝난 뒤 api_request_logs 에 기록 (401 로 막힌 요청 포함)
 ├─ Spring Security
 │   ├─ CORS                  허용 출처 확인 (사전 요청 OPTIONS 처리)
 │   ├─ JwtAuthenticationFilter  Bearer 토큰 → 서명·만료·사용자 활성·토큰 버전 확인 → UserContext 에 사용자 ID
 │   └─ 인가                  공개 경로가 아니면 인증 필요 → 없으면 401 JSON
 ├─ Controller                파라미터 검증(@Valid), 서비스 호출만
 ├─ Service                   CurrentUserService 로 현재 사용자 확인, 소유권 검사, 업무 로직
 └─ Repository → DB
```

**현재 사용자**는 `CurrentUserService.require()` 로만 얻습니다. 요청 파라미터에서 사용자 ID 를 받지 않습니다.
다른 사람의 리소스인지는 각 서비스가 `currentUser.assertOwner(...)` 로 확인하고, 다르면 403 입니다.

## 핵심 계산 규칙

### 사용 가능 자금과 자금 날씨

```
현재 잔액    = 자산 포함(includedInAssets=true) 계좌 잔액 합계
고정 지출    = 기간 안의 예정 이벤트 중 fixed=true, OUTFLOW, status=SCHEDULED 인 것의 합계
사용 가능 자금 = 현재 잔액 − 고정 지출
```

| 사용 가능 자금 | 날씨 | | 사용 가능 자금 | 위험도 |
| --- | --- | --- | --- | --- |
| 700,000 이상 | SUNNY 맑음 | | 500,000 이상 | GOOD |
| 300,000 ~ 699,999 | CLOUDY 흐림 | | 200,000 ~ 499,999 | CAUTION |
| 100,000 ~ 299,999 | RAINY 비 | | 200,000 미만 | DANGER |
| 100,000 미만 | STORM 폭풍 | | | |

- 기준 기간: 지정하지 않으면 사용자의 **기준 월**(`users.base_month`) 1일~말일
- **`PAID` 이벤트는 계산에서 빠집니다.** 이미 계좌 잔액에 반영됐기 때문입니다. 그래서 이벤트를 결제 완료로 바꾸면 "현재 잔액"과 "고정 지출"이 같이 줄고 **사용 가능 자금은 그대로**입니다. 이게 정상입니다.
- 날짜가 지났는데 아직 `SCHEDULED` 인 이벤트는 "아직 낼 돈"으로 계산합니다 ([07](07-현황과-남은-과제.md)의 남은 과제 참고).

### 잔액 예측 (`ForecastService.forecast`)

시작 잔액(현재 잔액)에서 출발해 기간 안의 `SCHEDULED` 이벤트를 날짜순으로 더하고 빼며, **가장 낮아지는 날(최저 잔액일)** 을 찾습니다. 예측의 날씨는 최저 잔액 기준입니다.

시드 기준 9월: `1,200,000 → 9/5 680,000 → 9/10 600,000 → 9/15 561,000(최저) → 9/25 3,061,000`

### 잔액 원장 (`LedgerService`)

**모든 잔액 변경은 "기존 효과 되돌리기 → 값 변경 → 새 효과 적용"** 순서입니다. 효과는 따로 저장하지 않고 엔티티의 현재 값에서 매번 계산합니다.

| 대상 | 잔액 효과 |
| --- | --- |
| 거래 `EXPENSE` + `accountId` | 계좌 −금액 |
| 거래 `INCOME` + `accountId` | 계좌 +금액 |
| 거래 `TRANSFER` | `accountId` −금액, `transferAccountId` +금액 |
| 거래 + `cardId` | **없음.** 카드 청구 이벤트가 `PAID` 될 때 결제 계좌에서 빠짐 |
| 거래에 계좌·카드 둘 다 없음 | 없음 (기록만) |
| 이벤트가 `PAID` 로 바뀜 | 이벤트의 `accountId` 에 `OUTFLOW` −, `INFLOW` + |
| 이벤트가 `PAID` 에서 벗어남 / 취소 | 위 효과를 되돌림 |

- 계좌와 카드는 둘 중 하나만 지정할 수 있습니다. 수정할 때 한쪽을 지정하면 다른 쪽은 자동으로 비워집니다.
- 결제 계좌가 없는 이벤트를 `PAID` 로 바꾸면 400 입니다.
- 시드 거래는 "이미 잔액에 반영된 과거 기록"이라 계좌를 연결하지 않았습니다.

### 이벤트 자동 생성 (`ScheduleService.materializeRange`)

반복 규칙과 카드 결제일에서 나오는 예정 이벤트는 **미리 만들지 않고, 그 달을 조회할 때 채웁니다.**
대시보드·예측·예정 이벤트 조회·시뮬레이션이 조회 전에 이 메서드를 부릅니다. 그래서 **이 조회들은 쓰기 트랜잭션**입니다(`readOnly` 아님).

| 출처 | 생성 규칙 | 중복 방지 |
| --- | --- | --- |
| 반복 규칙 | `MONTHLY`: 매달 `dayOfMonth`(말일 보정) / `WEEKLY`: 시작일부터 7일 간격 / `YEARLY`: 시작일과 같은 월·일. `startDate`~`endDate` 밖은 만들지 않음 | `(recurring_rule_id, event_date)` UNIQUE |
| 카드 | 전월 카드 `EXPENSE` 합계를 당월 결제일에 `CARD_BILL` 로. 합계 0 이면 안 만듦. 결제 계좌를 물려받음 | `(card_id, event_date)` UNIQUE |

- 이미 있는 이벤트는 새로 만들지 않고, **아직 지나지 않은 `SCHEDULED` 이벤트만** 원본(규칙 금액, 카드 사용액, 결제 계좌)에 맞춰 갱신합니다. 지난 이벤트와 결제 완료된 이벤트는 건드리지 않습니다.
- 규칙을 수정·비활성화하면 오늘 이후의 `SCHEDULED` 이벤트를 지우고(비활성이면 그대로 끝) 다시 만듭니다.
- 한 번에 최대 24개월까지만 펼칩니다.

## AI 구조

```
AgentController → AgentService.chat()
                    ├─ 최근 대화 10개 + 질문 → AgentAnswerClient.answer(request, AgentTools)
                    │     ├─ OpenAiCompatibleAgentAnswerClient: Tool Calling 반복 (최대 5회)
                    │     └─ RuleBasedAgentAnswerClient: 키워드로 의도 분류 → 같은 도구 호출
                    └─ 답변 + 호출한 도구의 인자·결과(tool_trace JSON)를 저장 → evidence 로 조회
```

- **도구 8개**(`AgentTools`): `get_dashboard`, `get_financial_events`, `get_forecast`, `get_budget_status`, `analyze_spending`, `simulate_spending`, `detect_recurring`, `get_alerts`. 모두 기존 서비스 메서드에 위임합니다.
- **답변기 선택**(`AgentClientConfig`): `AI_PROVIDER=auto`(기본)면 키 유무로 결정. 기동 로그의 `AI 답변기:` 줄에서 확인.
- **외부 AI 실패 시**: 예외를 삼키지 않고 경고 로그를 남긴 뒤 규칙 기반으로 대신 답하고, `provider` 를 `openai-compatible-fallback` 으로 표시합니다.
- **도구가 실패해도 대화는 계속**: 오류 메시지를 도구 결과로 AI 에게 넘깁니다.

## 트랜잭션에서 주의할 점

이 두 가지는 코드만 보면 이상해 보이지만 일부러 그렇게 만든 것입니다. **바꾸면 버그가 납니다.**

1. **`AgentService` 에는 클래스 수준 `@Transactional` 이 없습니다.**
   도구 하나가 실패하면(예: 없는 달의 예산) 그 서비스의 트랜잭션에서 예외가 납니다. `chat()` 전체가 한 트랜잭션이면 이 예외 때문에 트랜잭션이 **롤백 전용**으로 표시되고, AI 가 오류를 잘 처리해 답해도 커밋할 때 500 이 됩니다. 그래서 도구 호출과 메시지 저장이 각자 트랜잭션을 갖게 했습니다.

2. **예산은 `BudgetService.exists()` 로 먼저 확인한 뒤 `status()` 를 부릅니다.**
   같은 이유입니다. 다른 트랜잭션 안에서 `status()` 의 404 예외를 `try/catch` 로 잡아 넘기면, 잡았더라도 트랜잭션은 이미 롤백 전용이 됩니다. `AlertService`, `AgentTools`, `AgentService` 가 이 패턴을 씁니다.
