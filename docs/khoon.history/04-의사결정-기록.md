### D1. 반복 규칙 이벤트는 조회할 때 만든다
- **결정**: 규칙을 만들 때는 시작 월만 만들고, 나머지 달은 그 달을 조회하는 순간(`ScheduleService.materializeRange`) 만든다.
- **대안**: ① 생성 시 12개월치를 미리 저장 ② 저장하지 않고 조회 때마다 계산만.
- **이유**: 스케줄러가 필요 없고, 이벤트가 실제로 저장되므로 한 건만 결제 완료·취소할 수 있다(②는 불가).
- **주의**:
  - 대시보드·예측·예정 이벤트 조회·시뮬레이션이 **DB 에 쓴다**. 이 메서드들에 `@Transactional(readOnly = true)`를 붙이면 안 된다.
  - "이미 만들었는지" 판단을 위해 이벤트에 출처(`recurring_rule_id`, `card_id`)가 필요했다(V3). 제목 비교는 사용자가 제목을 바꾸면 중복이 생긴다.
  - 동시 요청에 의한 중복은 `(recurring_rule_id, event_date)`, `(card_id, event_date)` UNIQUE 로 막는다.
  - 한 번에 최대 24개월까지만 펼친다.

### D2. 카드 대금은 전월 사용분을 당월 결제일에 청구
- **결정**: 카드로 연결된 전월 `EXPENSE` 거래 합계를 당월 결제일의 `CARD_BILL` 이벤트로 만든다. 합계가 0 이면 만들지 않는다.
- **대안**: 당월 사용분 청구, 카드별 고정 예상 청구액.
- **이유**: 실제 카드사 방식과 가장 가깝다. 거래에 `card_id` 를 두면 실제 사용액을 따라간다.
- **주의**: 실제 카드사의 사용 기간(예: 전월 15일~당월 14일)과는 다를 수 있다. 결제일 이후에 전월 거래가 추가되면, 청구 이벤트가 아직 지나지 않았고 `SCHEDULED` 일 때만 금액이 갱신된다.

### D3. 지난 이벤트는 소급해서 바꾸지 않는다
- **결정**: 규칙 금액이나 카드 사용액이 바뀌어도, **오늘 이전 날짜이거나 결제 완료된** 자동 생성 이벤트는 그대로 둔다.
- **이유**: 지난 이벤트는 이미 있었던 일이다. 금액을 바꾸면 과거 기록이 거짓이 된다.
- **주의**: "오늘"은 서버 시간 기준이다. 그래서 배포 컨테이너의 시간대를 Asia/Seoul 로 고정했다(D18).

### D4. 사용 가능 자금의 의미를 유지하고 PAID 는 계산에서 뺀다
- **결정**: `사용 가능 자금 = 현재 잔액 − 기간 내 SCHEDULED 고정 지출`. `PAID` 이벤트는 고정 지출과 예측에서 제외한다.
- **이유**: 잔액이 실제로 움직이게 되면서(D5), 결제 완료된 이벤트까지 빼면 이중 차감이 된다. 결제 완료로 바꾸면 잔액과 고정 지출이 같이 줄어 **사용 가능 자금은 그대로**인 게 맞다.
- **주의**: 날짜가 지났지만 아직 `SCHEDULED` 인 이벤트는 "아직 낼 돈"으로 본다. 연체 처리 규칙은 없다([07](07-현황과-남은-과제.md)).

### D5. 잔액 효과는 저장하지 않고 "되돌리기 → 변경 → 적용"
- **결정**: 거래·이벤트가 잔액에 주는 효과는 엔티티의 현재 값에서 매번 계산한다(`LedgerService.effectOf`). 수정·삭제·상태 변경은 모두 이전 효과를 되돌린 뒤 새 효과를 적용한다.
- **대안**: 잔액 변경 이력 테이블(원장 저널).
- **이유**: 테이블과 코드가 단순하고, 규칙이 한 곳에 모인다.
- **주의**: 잔액 **변경 이력은 남지 않는다.** 감사 추적이 필요해지면 저널 테이블을 도입해야 한다. 잔액을 바꾸는 코드를 새로 짤 때는 반드시 `LedgerService` 를 거칠 것.

### D6. 결제 수단은 계좌와 카드 중 하나
- **결정**: 거래에 `accountId` 와 `cardId` 를 동시에 줄 수 없다(400). 수정할 때 한쪽을 보내면 다른 쪽은 자동으로 비운다.
- **이유**: 카드 거래는 청구 때 계좌에서 빠지므로 둘 다 있으면 이중 차감이다. 또 PATCH 에서 JSON 의 `null` 과 "안 보냄"을 구분할 수 없어서, "비우기"를 이렇게 표현했다.
- **주의**: 이체(`TRANSFER`)는 `accountId` 와 `transferAccountId` 가 모두 필요하고 서로 달라야 한다.

### D7. 잔액 직접 수정 허용 + 낙관적 잠금
- **결정**: `PATCH /accounts/{id}` 의 `balance` 로 덮어쓸 수 있다. `accounts.version` 으로 동시 수정 충돌을 409 로 알린다.
- **이유**: 거래를 빠짐없이 입력하지 않는 한 실제 통장과 어긋나므로 맞출 수단이 필요하다.
- **주의**: 직접 수정은 원장 규칙(D5) 밖에서 잔액을 바꾼다. 수정 이력이 없다.

### D8. 자산 삭제 정책
| 대상 | 삭제 시 | 이유 |
| --- | --- | --- |
| 계좌 | 거래·이벤트·카드·규칙이 쓰고 있으면 **409** | 연결된 이력이 끊긴다 |
| 카드 | **비활성화**(`active=false`) | 과거 거래와 청구 이력이 카드를 참조 |
| 카테고리 | 기본 카테고리는 409. 그 외는 거래를 미분류로 바꾸고, 걸린 예산 한도도 삭제 | 대상이 사라진 한도를 남기지 않음 |

- **예산은 카테고리를 이름으로 참조**한다(`budget_category_limits.category_name`, 처음 스키마 그대로). 그래서 카테고리 이름을 바꾸면 같은 사용자의 예산 한도 이름도 함께 바꾼다. ID 참조로 바꾸면 이 동기화 코드가 필요 없어진다.

### D9. 인증: 이메일·비밀번호 + 직접 구현한 JWT
- **결정**: 이메일·비밀번호(BCrypt) 가입·로그인. 토큰은 처음부터 있던 `AuthTokenService`(HS256 직접 구현)를 확장해 쓴다. Spring Security 로 토큰 없는 요청을 막는다. `X-User-Id`, `?userId=`, `dev-token` 은 폐기.
- **대안**: 소셜 로그인(플랫폼별 키가 필요해 AI 키처럼 막히는 부분이 생김), JWT 라이브러리.
- **이유**: 발표 시 설명이 쉽고 외부 의존이 없다.
- **주의**:
  - 로그인 실패 시 이메일·비밀번호 중 무엇이 틀렸는지 알려주지 않고, 없는 이메일도 같은 시간만큼 비밀번호 검사를 한다(가입 여부 노출 방지).
  - 가입자 ID 는 시퀀스(`users_id_seq`, 1000부터). 시드 사용자는 1번 고정이라 겹치지 않게 했다.
  - 운영(`postgres`)은 `JWT_SECRET` 이 없으면 기동하지 않는다. 16자 미만이면 기동 실패.

### D10. 토큰 무효화: 사용자별 토큰 버전
- **결정**: `users.token_version` 을 토큰에 담고, 로그아웃·비밀번호 변경 때 1 올린다. 버전이 다른 토큰은 거부.
- **대안**: refresh token, 토큰 블랙리스트.
- **이유**: 테이블 하나 없이 컬럼 하나로 끝난다. 인증 필터가 어차피 매 요청 사용자를 조회한다.
- **주의**: **기기별 로그아웃은 안 된다**(로그아웃하면 모든 기기에서 풀림). 비밀번호 변경은 새 토큰을 돌려줘 지금 기기는 유지.

### D11. 로그인 제한: 서버 메모리
- **결정**: 15분 안에 같은 이메일 5회, 같은 IP 20회 실패하면 429. 기록은 메모리에.
- **이유**: 홈서버 한 대 운영 전제. Redis 등 추가 구성이 필요 없다.
- **주의**:
  - 재시작하면 기록이 사라진다. 서버를 여러 대로 늘리면 공유 저장소가 필요하다.
  - **리버스 프록시 뒤에서는 `FORWARD_HEADERS_STRATEGY=framework`** 로 실제 IP 를 써야 한다. 안 그러면 모든 사용자가 프록시 IP 하나로 보여 IP 제한이 전체를 막는다. 프록시 없이 직접 노출할 때 켜면 헤더로 IP 를 속일 수 있다.

### D12. AI: Tool Calling, 규칙 기반도 같은 도구 사용
- **결정**: AI 는 도구 8개(`AgentTools`) 중 필요한 것을 골라 호출하고 결과 숫자로 답한다. 키가 없을 때 쓰는 규칙 기반 답변기도 **같은 도구**를 키워드로 골라 호출한다.
- **대안**: 매 질문마다 대시보드·이벤트·예측 전체를 프롬프트에 넣기(처음 방식).
- **이유**: 질문에 필요한 데이터만 쓰고, 시뮬레이션처럼 계산이 필요한 질문도 처리할 수 있다. 두 답변기가 같은 도구를 쓰니 결과 숫자가 일치한다.
- **주의**:
  - 외부 AI 실패 시 예외를 삼키지 않고 경고 로그 + 규칙 기반 대체 답변 + `provider` 에 `-fallback` 표시.
  - Tool Calling 반복은 최대 5회, 마지막 회차는 `tool_choice: none` 으로 답을 강제한다.
  - `tool` 메시지는 반드시 앞선 assistant 메시지의 `tool_call_id` 와 짝지어야 한다(처음 코드의 버그).
  - 이전 대화에서 조회한 도구 결과는 다음 질문에 넘기지 않는다(질문·답 문장만 10개).
  - `temperature` 를 지정하지 않았다(모델 기본값).

### D13. AI 제공자 자동 선택 (`auto`)
- **결정**: `AI_PROVIDER` 기본값 `auto`: `AI_API_KEY` 가 있으면 외부 AI, 없으면 규칙 기반. `rule-based`/`openai-compatible` 로 강제 가능. 잘못된 값이면 기동 실패.
- **이유**: 예전 기본값 `rule-based` 때문에 키를 넣어도 무시되는 일이 실제로 있었다.
- **주의**: 테스트는 `src/test/resources/config/application.properties` 로 **규칙 기반 고정**. 이걸 지우면 개발 PC 에 키가 있을 때 `mvn test` 가 유료 API 를 부른다.

### D14. AI 답변 근거를 저장한다
- **결정**: 답변할 때 호출한 도구의 인자·결과를 `agent_messages.tool_trace` 에 JSON 으로 저장하고, `evidence` 는 이걸 그대로 돌려준다.
- **이유**: "그 답을 왜 했나"는 답변 당시의 숫자여야 한다. 처음 코드는 조회할 때마다 현재 값을 다시 계산했다.
- **주의**: 10만 자를 넘으면 결과 본문을 빼고 이름·인자·오류만 남긴다(JSON 을 중간에서 자르지 않음).

### D15. 큰 문자열 컬럼은 TEXT 가 아니라 큰 VARCHAR
- **결정**: `agent_messages.content` 는 `VARCHAR(20000)`, `tool_trace` 는 `VARCHAR(100000)`.
- **이유**: `ddl-auto: validate` 에서 `TEXT`/`@Lob` 은 H2(CLOB)와 PostgreSQL(oid)의 검증 결과가 달라진다. 개발·배포 DB 가 다르므로 둘 다 통과하는 타입을 골랐다.

### D16. AgentService 는 트랜잭션으로 묶지 않는다
- **결정**: `AgentService` 에 클래스 수준 `@Transactional` 이 없다. 예산은 `exists()` 로 먼저 확인하고 `status()` 를 부른다.
- **이유**: 트랜잭션 안에서 다른 서비스의 예외를 잡아 넘겨도 트랜잭션은 롤백 전용이 되어 커밋 때 500 이 난다. 도구 하나의 실패가 대화 전체를 망치지 않게 했다. 자세한 설명은 [02](02-구조와-핵심-개념.md#트랜잭션에서-주의할-점).

### D17. 테스트 전략
- **결정**:
  - 테스트는 HTTP(MockMvc)로 API 를 호출해 검증한다. 내부 구현을 바꿔도 테스트는 그대로 둘 수 있다(리팩토링 때 실제로 테스트 파일을 안 바꾸고 117개 통과).
  - 모든 통합 테스트는 **매번 시드로 초기화**(`ApiTestSupport`)해 실행 순서와 무관하게 한다. H2 메모리 DB 를 모든 테스트 클래스가 공유하기 때문.
  - 기본 요청에 데모 사용자 토큰을 자동으로 붙인다(`DemoUserTokenConfig`). 인증 테스트는 토큰 없는 MockMvc 를 따로 만든다.
  - 외부 AI 는 **JDK 내장 HttpServer 로 만든 가짜 AI 서버**로 검증한다(추가 의존성 없음). 요청 본문을 캡처해 OpenAI 형식까지 확인한다.
- **주의**: 로그인 실패 기록이 테스트 간에 섞이지 않도록 `ApiTestSupport` 가 매번 비운다(모든 요청이 같은 IP 라서).

### D18. 배포 구성
- **결정**: `docker-compose.prod.yml` 로 앱 + PostgreSQL 16. DB 포트는 외부에 열지 않는다. 비밀값은 `.env`(git 제외).
- **세부**:
  - 컨테이너 시간대 **Asia/Seoul** 고정 (UTC 면 오전 0~9시에 "오늘"이 하루 어긋남)
  - `postgres` 프로필: `JWT_SECRET` 필수, 데모 데이터·초기화 API 꺼짐
  - 데모 데이터(`DEMO_DATA_ENABLED`)와 전체 초기화 API(`DEV_SEED_ENABLED`)를 **별도 스위치**로 분리. 시연용 데모 계정을 켜도 아무나 DB 를 지울 수는 없게.
  - CORS 허용 출처는 환경 변수. 토큰은 헤더로 보내므로 쿠키 자격 증명은 허용하지 않는다.
  - Docker 빌드에서 테스트는 생략한다(홈서버 빌드 시간). 배포 전 개발 PC 에서 `mvn clean test`.

### D19. 서비스 분리 (리팩토링)
- **결정**: 824줄의 `MoneyWeatherService` 를 대시보드·예측(`MoneyWeatherService`), 일정(`ScheduleService`), 거래(`TransactionService`), 예산(`BudgetService`), 데모 데이터(`DemoDataService`), 자산 조회(`AssetService` 로 합침)로 나눴다. 컨트롤러도 도메인별로.
- **원칙**: URL·요청·응답·트랜잭션 경계는 바꾸지 않는다. 테스트 파일을 고치지 않고 전부 통과하는 것으로 검증.
- **주의**: 응답·요청 DTO 는 소유 서비스 안의 `record` 로 둔다(예: `TransactionService.TransactionView`). 새 기능도 같은 방식을 따르면 된다.
